# Architecture Documentation

## System Overview

This proof-of-work system implements a microservices architecture with the following components:

### Microservices

```
┌─────────────┐
│   Client    │
└──────┬──────┘
       │ HTTP/REST
       ▼
┌─────────────┐
│   Gateway   │ (Port 8080)
│   Service   │
└──────┬──────┘
       │ gRPC
       ├──────────────────────┐
       │                      │
       ▼                      ▼
┌─────────────┐      ┌─────────────┐
│  Challenge  │      │  Verifier   │
│   Service   │      │   Service   │
│ (Port 50051)│      │ (Port 50052)│
└─────────────┘      └─────────────┘
```

## Service Responsibilities

### 1. Challenge Service (gRPC)
**File**: `services/challenge/server.go`

**Responsibilities**:
- Generate unique challenge IDs using UUID
- Accept difficulty level from clients
- Return challenge details (ID, difficulty, data, timestamp)

**gRPC Service Definition**: `api/proto/challenge.proto`
- Method: `GetChallenge(GetChallengeRequest) returns (GetChallengeResponse)`

**Port**: 50051

### 2. Verifier Service (gRPC)
**File**: `services/verifier/server.go`

**Responsibilities**:
- Verify proof-of-work solutions
- Compute hash from challenge ID, data, and nonce
- Validate hash has required number of leading zeros
- Return verification result

**gRPC Service Definition**: `api/proto/verifier.proto`
- Method: `VerifyProof(VerifyProofRequest) returns (VerifyProofResponse)`

**Port**: 50052

### 3. Gateway Service (HTTP REST)
**File**: `services/gateway/server.go`

**Responsibilities**:
- Provide HTTP/REST API for clients
- Translate REST requests to gRPC calls
- Route requests to appropriate backend services
- Handle JSON serialization/deserialization

**Endpoints**:
- `POST /v1/challenge` - Get a new challenge
- `POST /v1/verify` - Verify a proof
- `GET /health` - Health check

**Port**: 8080

## Communication Protocols

### gRPC (Internal Service-to-Service)
- **Protocol**: HTTP/2
- **Format**: Protocol Buffers
- **Benefits**:
  - Type-safe contracts
  - Efficient binary serialization
  - Bidirectional streaming support
  - Built-in service discovery with reflection

### REST (External Client-to-Gateway)
- **Protocol**: HTTP/1.1
- **Format**: JSON
- **Benefits**:
  - Easy to use with curl, browsers
  - Human-readable
  - Wide tool support
  - No special client libraries needed

## Data Flow

### Challenge Request Flow
1. Client sends HTTP POST to `/v1/challenge`
2. Gateway receives REST request, deserializes JSON
3. Gateway calls Challenge Service via gRPC
4. Challenge Service generates UUID and returns response
5. Gateway serializes response to JSON
6. Client receives challenge details

### Proof Verification Flow
1. Client computes proof-of-work locally
2. Client sends HTTP POST to `/v1/verify` with nonce
3. Gateway receives REST request, deserializes JSON
4. Gateway calls Verifier Service via gRPC
5. Verifier Service:
   - Computes hash using challenge ID, data, and nonce
   - Checks if hash meets difficulty requirement
   - Returns validation result
6. Gateway serializes response to JSON
7. Client receives verification result

## Core Library

### Proof-of-Work Package
**File**: `pkg/pow/pow.go`

**Functions**:
- `ComputeHash(challengeID, data string, nonce int64) string`
  - Computes SHA-256 hash of challenge data with nonce
  
- `VerifyProof(hash string, difficulty int32) bool`
  - Verifies hash has required leading zeros
  
- `FindNonce(challengeID, data string, difficulty int32, maxAttempts int64) (int64, string, bool)`
  - Brute-force search for valid nonce (client-side only)

## Build System - Bazel

### Why Bazel?

1. **Reproducible Builds**: Hermetic build environment ensures consistent results
2. **Fast Incremental Builds**: Only rebuilds what changed
3. **Multi-Language Support**: Native support for Go, Protocol Buffers, and more
4. **Scalability**: Can handle large monorepos efficiently
5. **Remote Caching**: Can share build artifacts across team

### Build Targets

```bash
# Build everything
bazel build //...

# Build individual services
bazel build //services/challenge
bazel build //services/verifier
bazel build //services/gateway

# Build client example
bazel build //examples/client

# Build core library
bazel build //pkg/pow

# Run tests
bazel test //...
bazel test //pkg/pow:pow_test
```

### Workspace Structure

**WORKSPACE**: Root configuration file
- Defines external dependencies
- Imports rules for Go and Protocol Buffers
- Sets up toolchains

**BUILD.bazel files**: Define build targets for each package
- Specify source files
- Declare dependencies
- Define library/binary outputs

**deps.bzl**: Centralizes Go dependencies
- Generated by Gazelle
- Can be manually edited
- Lists all external Go modules

## Protocol Buffers

### Why Protocol Buffers?

1. **Type Safety**: Strong typing prevents errors
2. **Backward Compatibility**: Can evolve APIs safely
3. **Code Generation**: Automatic client/server code
4. **Performance**: Efficient binary serialization
5. **Documentation**: Proto files serve as API docs

### Schema Files

**challenge.proto**:
```protobuf
service ChallengeService {
  rpc GetChallenge(GetChallengeRequest) returns (GetChallengeResponse);
}
```

**verifier.proto**:
```protobuf
service VerifierService {
  rpc VerifyProof(VerifyProofRequest) returns (VerifyProofResponse);
}
```

### Generated Code

Bazel automatically generates Go code from `.proto` files:
- Service interfaces
- Client stubs
- Message types
- Serialization methods

## Deployment Considerations

### Container Deployment
Each service can be containerized separately:
```dockerfile
FROM golang:1.21-alpine
COPY bazel-bin/services/challenge/challenge_/challenge /app/
ENTRYPOINT ["/app/challenge"]
```

### Kubernetes Deployment
Services can be deployed as separate pods:
- Challenge Service: Deployment + Service
- Verifier Service: Deployment + Service
- Gateway Service: Deployment + Service + Ingress

### Service Discovery
Currently uses hardcoded addresses. Production should use:
- Kubernetes DNS
- Consul
- etcd
- Or similar service mesh

## Security Considerations

### Current Implementation (Development)
- No authentication
- No TLS/SSL
- Insecure gRPC connections

### Production Requirements
1. **Authentication**: Add API keys or OAuth
2. **TLS**: Enable mutual TLS for gRPC
3. **Rate Limiting**: Prevent abuse
4. **Input Validation**: Validate all inputs
5. **Monitoring**: Add metrics and logging
6. **Secrets Management**: Use vault or k8s secrets

## Performance Characteristics

### Challenge Generation
- O(1) complexity
- Sub-millisecond response time
- Limited only by UUID generation

### Proof Verification
- O(1) complexity
- Single hash computation
- Sub-millisecond response time

### Client Proof Finding
- O(n) where n depends on difficulty
- Difficulty 4: ~10,000 attempts average
- Difficulty 5: ~160,000 attempts average
- Difficulty 6: ~2.5 million attempts average

### Scalability
- Challenge and Verifier services are stateless
- Can scale horizontally with load balancer
- No database required (challenges are ephemeral)
- Could add Redis for challenge persistence if needed
